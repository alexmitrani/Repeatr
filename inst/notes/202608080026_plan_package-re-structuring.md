# Repeatr / fugazi.db restructuring

## Context

Repeatr currently bundles three things that are conceptually separate: primary/raw data (scraped or hand-curated source files), the code that cleans/classifies/models that data into the package's ~40 `data/*.rda` objects, and the Shiny app that presents the results. This makes it hard to see what depends on what, and conflates "this is a fact about a Fugazi show" with "this is the output of a modelling choice."

The goal is to split primary data out into its own package, `fugazi.db` (an almost-empty public GitHub repo today), while keeping *all* processing code and *all* derived/modelled data in Repeatr. `fugazi.db` should also be structured so a future CRAN submission is realistic. The Shiny app's output must be unaffected — that's the regression check for the whole exercise. Along the way, data that turns out to be genuinely unused gets deleted rather than migrated, and every overlapping/patch-on-raw structure (two venue-coordinate files with different join keys, correction lookups bolted onto raw sources) gets collapsed into one clean, corrected primary source — per your explicit requests to keep fugazi.db clean.

Confirmed decisions this plan builds on:
- **All of fugazi.db's shipped data is `.rda`** in `data/`, lazy-loadable, one format throughout — no loose CSV/txt in the installed package. This is the CRAN-idiomatic shape for a data package (precedent: `nycflights13`, `babynames`, `gapminder`, `Lahman`) and it also happens to eliminate a redundancy already present in Repeatr today: `releases_songs_durations_wikipedia.csv` and `songvarslookup.rda` currently ship the same data twice, once as raw CSV and once as its literal `.rda` copy.
- fugazi.db gets one doc-only `R/data.R`-style file (roxygen blocks + bare string literals, no functions) for `?dataset` help pages, plus a vignette explaining the tables, their columns, join keys (`gid` above all), and worked examples — the sole exceptions to "no code in fugazi.db" (a vignette is documentation, not package code; its example chunks are `eval = FALSE` and reference Repeatr, since fugazi.db has nothing to execute them with).
- Repeatr's `DESCRIPTION` gets `Depends: fugazi.db` + `Remotes: alexmitrani/fugazi.db` for default runtime data access — a data-only dependency, doesn't conflict with "all code stays in Repeatr."
- Genuinely unused data is deleted, not migrated.
- All code — including the raw-refresh workflow and the script that builds fugazi.db's `.rda` objects from its editable raw sources — stays in Repeatr.

A key finding from research: **`inst/shiny/Fugazetteer/app.R` doesn't use the package's own venue x/y at all** — at startup it re-fetches coordinates live from a Google Sheet via `gsheet2tbl()` and overwrites whatever `othervariables`/`shows_data` provided (`app.R:44-70`, `200-217`). So the deployed app's map coordinates were never tied to the package's own geocoding pipeline in the first place, which meaningfully de-risks the geocoding consolidation below — it can't change what the app renders, only what the package's own exported data objects contain.

## fugazi.db package layout

```
fugazi.db/
  DESCRIPTION, NAMESPACE, LICENSE, README.md, .Rbuildignore, .gitignore
  R/
    data.R                    # doc-only: roxygen @format/@source/@section Provenance + bare strings
  data/                       # shipped .rda objects — see table below
  data-raw/                   # human-editable raw sources, .Rbuildignore'd (data, not code)
    fls_data.csv
    fls_tags.txt
    releases_songs_durations_wikipedia.csv
    releases.csv
    song_tempo_bpm_data.csv
    fls_venue_geocoding.csv
  man/                        # generated by devtools::document()
  vignettes/
    Data-Catalogue.Rmd        # tables, columns, join keys (gid, songid analogue if any), examples
```

`data-raw/` is not a novelty here — it's the same convention Repeatr's own `data-raw/build_data.R` already uses (`.Rbuildignore`d, not part of the built package), just holding the plain editable files instead of a script (which can't live here, since it's code). This isn't the kind of duplication flagged earlier — that was about *two different sources* both claiming authority over the same fact with different join keys (`fugazi-small.csv` vs. `fls_venue_geocoding_v2.csv`, or a patch file silently overriding a subset of rows). This is one source of truth in two representations: an editable master a human or scraper updates directly, and a generated, typed, documented build artifact. Every raw CSV/txt file that isn't hand-edited on an ongoing basis (i.e. everything except the geocoding file and `song_tempo_bpm_data.csv`) could in principle skip `data-raw/` and just be regenerated on demand, but keeping all six there uniformly is simpler than special-casing.

## Venue-geocoding consolidation (three overlapping sources → one)

Today `R/Repeatr_1.R` resolves venue x/y through **four** mechanisms: `fugazi-small.csv` (joined by `date`+`venue` at line 163, a baseline), ~20 hardcoded per-venue/per-gid `ifelse()` corrections (lines 166-364 — these stay as code, they're genuine overrides of wrong scraped data, not missing-coverage fallbacks), `fls_venue_geocoding_v2.csv` (joined by `country`+`city`+`venue` at lines 397-411, overrides x/y wherever it matches and sets `checked=1`), and `othervariables_patch.csv`.

`othervariables_patch.csv` does the same job as `fugazi-small.csv`: confirmed by direct inspection (`R/Repeatr_1.R:222`, `bind_rows(othervariables, othervariables_patchfile)`) that its 23 rows are full-row duplicates of existing `fls_data.csv` shows — every field (venue, attendance, recorded_by, tour, date) matches the original row exactly except x/y. Because `bind_rows` runs before the `filter(is.na(x)==FALSE)` + `group_by(gid) %>% slice(1)` dedup at lines 445-453, a patch row only survives when the original row for that `gid` got dropped for lacking coordinates — i.e. it's x/y "rescue" data for venues the rest of the chain fails to resolve.

1. **Identify fallback-only venues from `fugazi-small.csv`.** Insert a temporary diagnostic right after line 414 (after `select(-link_x, -link_y, -geocoding_check)`, before the suffix-stripping block at 416+, so `city` is still in the v2-compatible disambiguated form):
   ```r
   fallback_only_venues <- othervariables %>%
     filter(checked == 0, is.na(x) == FALSE) %>%
     distinct(country, city, venue, x, y) %>%
     arrange(country, city, venue)
   ```
2. **Fold in `othervariables_patch.csv` directly** — its 23 rows already give `(country, city, venue, x, y)` in the post-disambiguation-suffix city form, matching step 1's output and the v2 join's own key.
3. **Build the merged object.** Take your freshly-updated `fls_venue_geocoding_v2.csv` (which now mirrors the live Google Sheet exactly) as the base schema (`country,city,venue,googlemaps_hyperlink,find1,find2,find3,y,x,test_coordinates`), append one row per entry from steps 1-2 (helper columns blank — `R/Repeatr_1.R` only ever selects `country,city,venue,x,y`), dedupe on `(country, city, venue)`, sort. This becomes `fugazi.db/data-raw/fls_venue_geocoding.csv`, then `fugazi.db/data/fls_venue_geocoding.rda`. Neither `fugazi-small.csv` nor `othervariables_patch.csv` moves under its own identity — both are fully consumed here.
4. **Code change in `R/Repeatr_1.R`:**
   - Delete lines 98-117 (the `fugazi-small.csv` read + column drops) and line 163 (the fugazi-small join).
   - Delete line 222 (`bind_rows(othervariables, othervariables_patchfile)`) and its read site, plus the explanatory comment at ~219-221.
   - Add `x = NA_real_, y = NA_real_` to `othervariables`'s first `mutate()`, before the correction blocks at 166+ (every branch there already overwrites or falls through via `ifelse(cond, new, x)`).
   - Replace the line-397 file read with a direct reference to the `fls_venue_geocoding` object (see parameterization below).
   - No change needed to the disambiguation-suffix injection (224-237) or stripping (416+).
5. **Verify:** run `Repeatr_1()` pre- and post-merge, diff `othervariables$x/y` and `shows_data$latitude/longitude` by `gid` across all ~1000+ shows, not just the ones expected to change.

## Parameterizing the pipeline functions

Since the primary data is now lazy-loaded `.rda` (not files on a path), "pointing a function at external data" naturally becomes **passing a data frame directly** as an optional argument, rather than a file path — there's no path a normal user reads once it's package data.

`Repeatr_1()`'s existing `mycsvfile`/`mysongdatafile`/`releasesdatafile` (file-path) parameters are replaced with data-frame equivalents, e.g. `myfls_data = NULL`, `mysongvarslookup = NULL`, `myreleases = NULL`, each defaulting to the bare fugazi.db object (`fls_data`, `songvarslookup`, `releases`) when `NULL` — simpler than the old `system.file()` fallback, since `Depends: fugazi.db` already attaches these by name. Add the same pattern for the two reads that currently have *no* override at all: `myfls_venue_geocoding = NULL` (defaults to `fls_venue_geocoding`) and `myfls_tags = NULL` (defaults to `fls_tags_raw`, replacing the `fls_tags_importer(myfilename = "fls_tags.txt")` call — `fls_tags_importer()` itself is no longer needed in the default pipeline, only by the fugazi.db build step below).

This still satisfies "point the functions at external data" in full: a caller can pass *any* data frame, built however, from anywhere — strictly more flexible than a file-path convention, since it doesn't assume the override lives on disk in any particular shape.

`output_dir = NULL` stays as previously planned on all six pipeline functions (`Repeatr_1` through `Repeatr_6`), defaulting to today's `paste0(getwd(), "/data")` — this is about where Repeatr's own derived output lands, unrelated to fugazi.db's format, so it's unchanged by this revision. `Repeatr_2()`/`Repeatr_5()` keep an `input_dir` for where the 6 output-export CSVs get written (`system.file("extdata", package = "Repeatr")` default, unchanged).

## New: a build step for fugazi.db's own data

Since fugazi.db can hold data but not code, the `data-raw/*.csv|txt` → `data/*.rda` conversion for fugazi.db lives in Repeatr, as a new function (e.g. `build_fugazidb_data(fugazidb_dir)`) alongside the existing pipeline functions. It's a small, mechanical step per object: `read.csv()` (or `fls_tags_importer()` for the tags file) each `data-raw/` source, `save()` the result into `fugazi.db/data/`. This is the *ongoing* counterpart to the one-time bake-ins above — once the one-time cleanup is done, future updates to any of these six sources (a new BPM reading, a synced geocoding sheet, a fresh scrape) go straight into `data-raw/`'s plain files by hand or via `scrape_fls_shows()`, and this function turns them into the shipped `.rda` objects. No further correction-lookup files should be needed going forward; a future one-off inconsistency (e.g. a new tag typo) gets fixed by editing `data-raw/fls_tags.txt` directly, not by reintroducing a patch file.

## Updated `data-raw/build_data.R` — three-stage flow

```r
library(Repeatr)

# Stage A — raw refresh, writing into a fugazi.db checkout's data-raw/ -------
fugazidb_dir <- "../fugazi.db"   # sibling checkout, adjust as needed

fls_data <- scrape_fls_shows(update_existing = TRUE, sleepseconds = 2,
                              mycsvfilename = file.path(fugazidb_dir, "data-raw", "fls_data.csv"))
# Venue coordinates: overwrite data-raw/fls_venue_geocoding.csv by hand from
# the Google Sheet snapshot. Tags/duration: export from kid3 straight into
# data-raw/fls_tags.txt. Song tempo: edit data-raw/song_tempo_bpm_data.csv by hand.

# Stage B — build fugazi.db's data/*.rda from its data-raw/ sources ---------
build_fugazidb_data(fugazidb_dir = fugazidb_dir)
# Commit + push fugazi.db, then reinstall it so system.file()/library()
# resolves the refreshed objects: devtools::install_github("alexmitrani/fugazi.db")

# Stage C — rebuild Repeatr's derived data -----------------------------------
Repeatr_Updatr(really = "really", update_stacks = TRUE)
```

Reinstalling fugazi.db between Stage B and Stage C is unavoidable if the pipeline functions default to the *attached* `fugazi.db` objects — that's how `Depends:` resolves. `Repeatr_1(myfls_data = fugazidb_data$fls_data, ...)` (loading straight from a local `fugazi.db/data/*.rda` via `load()`) can skip the reinstall for quick local iteration, since the data-frame-argument design supports that directly.

## DESCRIPTION / NAMESPACE

**Repeatr**: add `fugazi.db` to `Depends:`, add `Remotes: alexmitrani/fugazi.db`. No other dependency changes.

**fugazi.db**: `Package: fugazi.db`, `LazyData: true`, `Encoding: UTF-8`, `Roxygen: list(markdown = TRUE)`, matching `RoxygenNote`, `License:` (match Repeatr's GPL(>=3) unless you'd prefer a data-friendlier license like CC0/CC-BY for a pure-data package — worth a quick decision, doesn't block the rest of the plan), `URL`/`BugReports` pointing at the GitHub repo, no `Imports`/`Depends` beyond base R. Generate the skeleton with `usethis::create_package("fugazi.db")`, strip its default boilerplate. `devtools::document()` generates `NAMESPACE`/`man/*.Rd` from the doc-only `R/data.R`.

For future CRAN-readiness specifically: keep `data-raw/` `.Rbuildignore`d (already required either way), make sure every object in `data/` has a complete roxygen block (`@format` with a full column table, `@source`, `@section Provenance`) so `R CMD check` raises no "undocumented data" notes, and keep the DESCRIPTION's `Authors@R`/`Title`/`Description` fields filled in properly since CRAN checks those closely even for data-only packages.

## Points flagged for your awareness (not blocking, but worth knowing)

- The new merged geocoding object reuses the name `fls_venue_geocoding`, previously the now-deleted fossil file's name — a deliberate content replacement. Say if you'd rather use a distinct name for clarity.
- `nscmov()` becomes effectively dead code once its default input file is gone (still callable with an explicit path). Left in place as-is; flag if you'd rather see it formally deprecated.
- The 23 venues folded in from `othervariables_patch.csv` were never checked against `fls_venue_geocoding_v2.csv` — worth a quick visual scan of the merged file for near-duplicates once it's built (exact-match dedup won't catch a spelling variant).

## Verification (the regression check)

1. **Baseline**: on current `main`, run `Repeatr_Updatr(really = "really", update_stacks = TRUE)` from a clean checkout, snapshot every `data/*.rda` (e.g. `tools::md5sum()`) and the 6 output CSVs.
2. **Post-migration**: after all changes, reinstall both packages and re-run `Repeatr_Updatr(really = "really", update_stacks = TRUE)` with defaults left as-is (exercising the normal workflow).
3. **Diff every object**: load both versions of all ~40 `data/*.rda` objects and `identical()`/`all.equal()` them — not just the ones this migration touches. Diff the 6 output CSVs the same way.
4. **Geocoding-specific check**: diff `othervariables$x/y` and `shows_data$latitude/longitude` by `gid`, pre/post merge, across all shows.
5. **Venue-name and tag-name bake-in check**: diff `othervariables$country/city/venue` and `fls_tags`/`fls_tags_show`/`duration_summary`/`duration_data_da`/`cumulative_*` pre/post.
6. **Shiny app smoke check**: `shiny::runApp("inst/shiny/Fugazetteer")` before/after, spot-check pages that don't depend on live-fetched data. Confirmatory, not primary evidence — steps 3-5's byte-identity checks are.
7. **`devtools::test()`** on Repeatr — cheap, covers `songid`/`alt` invariants.
8. **`devtools::check()`** on both packages — for fugazi.db specifically, confirm a clean, `NOTE`-free check as a proxy for future CRAN-readiness (no undocumented data, valid DESCRIPTION fields, reasonable installed size).
